# exp-recorder：任务经验固化

## 概述

**每个非平凡任务都应留下一条教训。** 本技能把这件事标准化：任务收尾后扫描对话，提炼洞察，写成编号 `.exps/NNN-<title>.md`，并更新索引。目标是**机构记忆**——下一个人（或未来的你）不必重新踩一遍。

开始时声明：「Using exp-recorder skill to capture lessons from this task.」

## 何时使用

任务中出现以下任一即用：

- 一个非显然、需要调试的错误
- 针对库 / API / 操作系统的 workaround
- 版本 pin 或依赖冲突
- 中途纠正的错误假设
- 打破旧代码的 API 变更
- 效果好、应复用的模式
- 用户确立项目约定的决策

**不用**于平凡任务（一行修复、错别字、无意外的机械改动）。

## 标准格式

每个 `.exps/NNN-<title>.md` 必须遵循模板：

```markdown
# NNN · 简短标题

> YYYY-MM-DD · severity · module/component

## 症状
（粘贴真实报错 / 用户观察 / 失败表现，要具体。）

## 根因
（为什么发生——机制层，不只是表象。）

## 解决
（实际代码 / 配置改动。给 before/after diff 或最终片段。）

## 验证
（如何确认修好。跑测试、贴输出。）

## 预防
（下次怎么避免。checklist、lint 规则、文档备注等。）
```

- **severity**：`low`（表面/轻松）· `medium`（真 bug，<1h 修好）· `high`（多小时调试）· `blocker`（不修没法继续）。
- **title**：kebab-case，≤60 字符，描述**症状或根因**而非动作。例：`tachyon-rejects-default-ua`、`bubbletea-v2-migration`。

## 索引 `.exps/README.md`

顶部维护 `## 索引` 表，列为 `#` · `标题` · `关键问题` · `日期`，新增条目即更新，按编号升序：

```markdown
| #   | 标题                                     | 关键问题       | 日期       |
| --- | ---------------------------------------- | -------------- | ---------- |
| 001 | [tachyon-rejects-default-ua](001-....md) | 403 · UA 真值  | 2026-08-04 |
| 002 | [trpc-agent-go-api-deltas](002-....md)   | 3 处破坏性变更 | 2026-08-04 |
```

## 工作流

1. **扫描对话**：找浪费过时间的错误/错误假设、奏效的 workaround、应复用的模式、用户的纠偏。
2. **对 `.exps/` 去重**：读 `.exps/README.md`；已有同类教训就**更新**（改日期、补上下文），不新建。
3. **取下一个编号**：扫 `.exps/NNN-*.md` 取最大 N 加一，补零到 3 位（`001`、`042`）。
4. **写文件**：用上面的模板，贴真实报错、真实代码、真实命令；含糊条目以后没用。
5. **更新索引**：把新行加入 `.exps/README.md`，保持有序。
6. **交叉引用**：与旧条目相关就在正文里引用其编号（「see also 002-...」）。
7. **提炼习惯**：足够通用的教训，追加进项目 `development-habits.md` 对应章节——习惯可跨项目复用，经验是本项目专属。

## 如何从上下文学习

写之前：

- 读 `.exps/README.md`，看已有什么、用什么风格。
- 读项目的 `development-habits.md`（若有），对齐既有元模式。
- 读 1–2 条现存 `.exps/` 条目，吸收偏好的细节粒度与代码片段风格。

这样新条目才与项目积累的知识一致。

## 反模式

- ❌ 含糊条目：「修了个 bug」没用——贴报错。
- ❌ 给平凡修复写条目（错别字、单行改动、纯机械重构）。
- ❌ 编号乱序——先读现有索引。
- ❌ 省略「预防」——那是最有价值的部分，它能阻止问题复发。
- ❌ 只叙述做了什么——聚焦教训，不是故事。
- ❌ 把无关教训并进一条——一个 bug、一个根因、一个文件。

## 好条目要点

报错原文已粘贴、根因解释到机制、解决是可直接套用的代码片段、预防项可执行、验证有命令输出支撑。

- `systematic-debugging`：产生多数 exp 条目的调试框架。
- `verification-before-completion`：写「已验证」前给出新鲜证据。
- `code-review-and-quality`：沉淀前先自查产物。
