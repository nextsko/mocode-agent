# Safe Refactor（安全重构）

重构 = **改变结构、不改变行为**。本 skill 只做一件事：在结构编辑前后用同一套证明夹住它（verification brackets structural edits）。先定义**行为保持边界**，再建立验证，之后才动结构。

## 铁律

```
未建立验证之前，不做结构编辑
未保持行为之前，不宣称重构完成
```

**把功能变更排除在重构之外。** 重构 PR 里混入行为变更＝两者都无法可靠验证。要加功能就单开一个变更。

## 工作流程

### 1. 定义行为保持边界

动手前写清楚：

- **哪些行为必须原封不动**：公开接口的输入/输出、错误模式与错误类型、调用顺序、副作用时机、兼容性承诺。
- **哪些明确在范围内**：允许改变的结构——提取、合并、移动所有权、重命名、替换内部实现。
- **哪些明确排除**：不在本次重构中触碰的行为或接口（例如：不改序列化格式、不改超时语义）。
- **行为边界之外的东西写下来**，因为「保持不变」的默认清单里往往藏着没被注意到的契约。

边界不清楚时先问用户，不要用「顺手改一下」来填空白。

### 2. 建立验证（先于结构编辑）

选择能证明「行为未变」的验证，并在**改动前跑一次、记录基线**：

- 优先**现有测试**：全量跑一遍，确认当前是绿的。绿之前不要开始。
- 覆盖不足就用 `test-driven-development` 为**将要保持的行为**补上特征测试（characterization test），watch it fail → 实现 → watch it pass。
- 无法自动化时（外部系统、时序）定义可复现的手工验证步骤，把命令与预期输出写下来。
- 对复杂系统，按 `systematic-debugging` 的多组件方法在边界处加诊断输出，便于对比前后。

**同一套证明在改动后要能原样复跑。** 若验证本身也改了，它就不再能证明行为未变。

### 3. 逐步做结构编辑

- **一次只移动一个所有权边界。** 一次重命名、一次提取、一次合并——不要打包成一锅。
- **保留公开接口。** 除非显式在范围内，否则不改签名、不改语义、不改兼容性。
- **保留失败行为**：错误类型、错误消息、异常传播、重试/超时语义，默认都应不变。
- **保留顺序**：初始化顺序、事件顺序、副作用顺序都算行为。
- **保持中间状态可构建、可测试。** 每一步提交后代码都应能编译、能跑测试。宁可多几个小 commit，也不要一个「大爆炸」。
- **不因正确性之外的理由增长依赖或配置。** 重构不是升级库、加抽象层、引入框架的借口。
- 每一小步后跑验证；红了立即回退该步，而不是叠加修复。

### 4. 复跑同一证明并收尾

- 跑**与第 2 步完全相同的**验证；确认全部通过且输出干净（无新错误、无新告警）。
- 确认行为匹配**且**目标结构达成——两者缺一都不算完成。
- 若为保持行为而写了特征测试，决定其去留：描述行为的保留，纯临时的删除并说明。

## 保留清单（默认不变，除非显式改）

| 维度 | 必须保留的示例 |
|------|----------------|
| 公开接口 | 函数/方法签名、类型、参数默认值、返回形状 |
| 失败行为 | 错误类型与消息、异常边界、失败重试与时序 |
| 顺序 | 初始化、事件发射、副作用发生顺序 |
| 兼容性 | 序列化格式、协议、持久化 schema、API 版本 |
| 可观测性 | 日志/指标的语义（新增可以，语义别悄悄改） |

改动其中任何一项，都必须显式写进第 1 步的边界并作为独立变更处理。

## 常见反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 重构中顺手改 bug / 加功能 | 行为变更无法与结构变更区分，验证失效 | 拆成两个变更，先重构再改行为 |
| 「反正要重写，直接删旧代码」 | 丢失未记录的行为契约 | 先写特征测试钉住行为，再动结构 |
| 一口气大改，最后才跑测试 | 无法定位是哪一步破坏行为 | 一次一个边界，每步跑验证 |
| 中间状态故意留红的 | 破坏可构建、可测试纪律 | 让每步都绿，必要时先加适配层再删除 |
| 为了「更干净」引入新依赖/抽象 | 正确性无关的增长，扩大风险面 | 除非正确性需要，否则不加 |
| 验证也跟着改 | 证明不了「行为未变」 | 前后复用同一套证明 |
| 追求一次到位、不做回退准备 | 失败成本放大 | 用小 commit，红了回退单步 |

## Verification Checklist

完成前逐条确认：

- [ ] 已写下行为保持边界（保留什么 / 改什么 / 排除什么）
- [ ] 改动前验证为绿，且记录基线
- [ ] 覆盖不足处已补特征测试（先失败、后通过）
- [ ] 每次只移动一个所有权边界，每步可构建、可测试
- [ ] 公开接口、失败行为、顺序、兼容性均未在范围外被改动
- [ ] 未因正确性之外的理由增加依赖或配置
- [ ] 改动后用**同一套**证明复跑，全部通过且输出干净
- [ ] 行为匹配且目标结构达成，才宣称完成

任一条不满足＝重构尚未安全完成。

## 与其他 skill 的关系

- `test-driven-development`：补特征测试、watch it fail、实现、watch it pass 的标准循环。
- `systematic-debugging`：重构中行为意外改变时，先找根因，不要在症状上叠加修复。
- `codebase-design`：判断「该提取还是该合并」时用深模块词汇（interface / seam / depth）决定结构目标。
- `code-review-and-quality`：评审重构 diff 时重点看契约、错误模式与兼容性。
- `security-and-hardening`：重构触及认证、输入校验、密钥、权限检查时，保持这些边界不被削弱。
