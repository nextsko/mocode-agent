# Karpathy Guidelines：减少 LLM 常见编码错误的行为准则

源自 [Andrej Karpathy 对 LLM 编码陷阱的观察](https://x.com/karpathy/status/2015883857489522876)。目标是把"自信却看似合理"的错误挡在提交之前。

**取舍（Tradeoff）**：本准则偏向**谨慎而非速度**。琐碎任务（改文案、一行修复）用判断力放行，不要为流程而流程。

## 1. 先想后写（Think Before Coding）

**不要假设。不要藏起困惑。把取舍摆到台面上。**

动手前：

- **显式陈述假设**；不确定就问，不要用沉默的猜测填补空白。
- **存在多种解释时全部列出**——不要默默挑一个。让用户裁决方向。
- **有更简单的方案就说出来**；必要时顶回去（push back），不要为了顺从而实现复杂路线。
- **有不明白的地方就停下**：命名困惑点，然后提问。带着误解写代码是最贵的错误。

对照 `code-review-and-quality`：作者对自己未言明的假设是盲的，问题越早暴露成本越低。

## 2. 简单优先（Simplicity First）

**解决问题的最少代码，不做任何投机性设计。**

- 不加超出需求的功能。
- 不为单次使用的代码造抽象。
- 不加没被要求的"灵活性""可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而 50 行可以解决——重写。

自问："资深工程师会不会说这过度复杂了？" 会，就简化。

搭配 `code-review-and-quality` 的 Readability 轴：抽象要配得上其复杂度，第三次使用场景出现前不要泛化。

## 3. 外科手术式改动（Surgical Changes）

**只碰必须碰的，只清理自己造成的混乱。**

编辑既有代码时：

- 不"顺手改进"相邻的代码、注释或格式。
- 不重构没坏的东西。
- 匹配既有风格，即使你自己会用另一种写法。
- 发现无关的 dead code——**提出来，但不要删除**。

当你的改动产生孤儿时：

- 移除**因你的改动**而变得未使用的 import/变量/函数。
- 不删除既有的 dead code，除非被明确要求。

**检验标准**：每一行改动都能直接追溯到用户的请求。多出来的改动就是 scope creep。

这与 `code-review-and-quality` 的"重构与 feature work 分开提交"一致——一个变更只解决一件事。

## 4. 目标驱动执行（Goal-Driven Execution）

**定义成功标准，循环到验证通过为止。**

把任务翻译成可验证的目标：

| 原始任务 | 可验证目标 |
|----------|-----------|
| "加校验" | "为非法输入写测试，然后让它们通过" |
| "修 bug" | "写一个能复现它的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都通过" |

多步任务先给出简短计划，每一步都带验证点：

```
1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]
```

**强成功标准让你能独立循环**；弱标准（"让它能跑"）会逼你不断回来澄清。

- 计划怎么写、怎么落盘，见 `writing-plans`。
- 失败与 bug 的根因调查，见 `systematic-debugging`——不要靠猜测试错。
- 完成声明前必须有新鲜证据，见 `verification-before-completion`。

## 红旗清单

出现以下任一信号，停下来重读上文：

- [ ] 我在没陈述假设的情况下就动手了。
- [ ] 有多个合理解释，但我只实现了一个。
- [ ] 我加了没人要求的功能、开关或抽象层。
- [ ] 我改了与任务无关的行、注释或格式。
- [ ] 我删了既有 dead code，却没有先征询。
- [ ] 我的任务没有可验证的成功标准，只靠"看起来对了"。
- [ ] 改动大到无法逐行追溯到用户请求。

## 相关技能

- `writing-plans`：把可验证目标落实成逐任务实现计划。
- `code-review-and-quality`：五个评审维度与批准标准，覆盖本准则的可读性/架构要求。
- `systematic-debugging`：目标驱动执行中失败路径的根因调查方法。
- `verification-before-completion`：完成声明前提供新鲜证据。
