# 先调查，后改动（Investigate First）

## 概述

在修改产品代码之前，先收集证据。

核心一句话：**证据不足不下手；没有一个可信机制能解释全部证据之前，不编辑产品代码。**

## 何时使用

- 失败原因不明（unknown cause）
- 间歇性行为（intermittent behavior）
- 性能回退（performance regression）
- 需要按证据排序假设的调查

与 `systematic-debugging` 的关系：本技能聚焦**诊断阶段的纪律**；`systematic-debugging` 提供从根因到修复的端到端四阶段流程。诊断完成、任务授权修复后，转入其 Phase 4，并用 `test-driven-development` 写失败测试、`verification-before-completion` 验证。

## 铁律

```
NO PRODUCT-CODE EDITS BEFORE A CREDIBLE MECHANISM
```

在能命名一个可信机制之前，不要改产品代码。可以加临时诊断 instrumentation，但不要"试试看"式地改逻辑。

## 诊断流程

1. **区分症状与推断原因**：observed symptom ≠ inferred cause。记录你实际观察到的，与你的猜测分开。
2. **追踪输入、状态转换、所有权边界与失败输出**：数据从哪来、经过哪些状态、在哪个边界变坏。
3. **按证据与廉价证伪价值排序假设**：优先能被低成本实验快速证伪的假设。
4. **不要编辑，直到一个可信机制能解释证据**：机制必须能解释全部关键观察，而不只是一部分。
5. **证据足以命名原因或确切阻塞点时停止探索**：目标是定位，不是无限调查。

## 症状 vs 原因

| 症状（可观察） | 需要推断的 | 常见错误 |
|----------------|------------|----------|
| "请求超时" | 超时发生在哪一层、哪个操作慢 | 直接给慢查询加缓存 |
| "偶发失败" | 触发条件、竞态、时序 | 加重试掩盖竞态 |
| "结果不对" | 坏值从哪进入、在哪被转换 | 在输出端打补丁 |
| "构建失败" | 哪一步、环境还是代码 | 反复重跑期望自愈 |

## 证据收集要点

- **读完整错误信息与堆栈**：不要跳过 warning；记下行号、文件路径、错误码。
- **稳定复现**：能否可靠触发？确切步骤是什么？每次都发生吗？不能复现就先收集更多数据，别猜。
- **检查最近变更**：`git diff`、最近 commit、新依赖、配置与环境差异。
- **多组件系统在边界加诊断 instrumentation**：在每个组件边界记录进入/离开的数据与环境配置传播，运行一次看"在哪里断"。
- **追踪数据流到源头**：坏值从哪里产生？谁用坏值调用了这里？一路向上追，修复点在源头而非症状处。

## 假设排序

- 每个假设写成："我认为 X 是原因，因为 Y"——具体、可证伪。
- 先做**最廉价**、能最大程度排除可能性的实验（cheap falsification value）。
- 一次只验证一个变量；不要一次改多处。
- 假设被证伪就记录并形成新假设，不要在旧假设上叠加更多修改。

## 何时停止

当证据足以**命名原因或确切阻塞点**时停止探索并汇报。不要追求 100% 确定性，也不要因为"还想再看看"而拖延。

## 汇报格式

只报告**原因与证据**，不要顺手修复：

```
CAUSE: <可复现、可解释全部关键观察的机制>
PROOF: <支撑证据——复现步骤、日志/堆栈、边界观测、实验结论>
CONFIDENCE: <高/中/低，及尚存的未知>
NEXT: 需要授权才能实施修复（或：任务已授权，转入 systematic-debugging Phase 4）
```

**除非任务明确授权实现，否则不做修复。** 调查者不等于修复者。

## 常见合理化与红旗

| 合理化 | 现实 |
|--------|------|
| "原因很明显，直接改" | 看起来明显往往是症状；先验证机制再动手。 |
| "我边改边查" | 改动会引入新变量，污染后续证据。先查后改。 |
| "先加重试兜住" | 重试掩盖竞态，把间歇故障变成更难查的问题。 |
| "复现不了但先猜一个" | 不可复现时更需要 instrument 收集数据，而非猜测。 |
| "多改几处一次试" | 无法隔离是哪个改动起作用/致坏。 |

红旗：还没理解机制就动手改；把症状当原因；一次验证多个变量；用重试/缓存掩盖根因；在未授权时提交修复；忽略 warning 与堆栈。

## 相关技能

- `systematic-debugging`：诊断之后从根因到修复的完整四阶段流程。
- `test-driven-development`：用失败测试锁定并复现根因。
- `verification-before-completion`：声明"已定位/已修复"前先给出证据。
- `code-review-and-quality`：修复方案合并前的评审。
