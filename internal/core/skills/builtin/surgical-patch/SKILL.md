# Surgical Patch（外科式修补）

## 概述

在**拥有错误行为的最窄责任层**上修复。改动越小、越聚焦，越容易评审、验证与回退。

核心一句话：**先定位负责机制，只在拥有该行为的层改动，只加任务相关的 regression proof。**

## 何时使用

- 修复 bug，或做小的行为改动
- 需要 regression proof，并保护周边行为不被波及
- 补丁容易「顺手」扩散到清理、重命名、抽象

**不适用**：新 feature / 大切片（见 `lean-build`）；纯验证任务（见 `verify-and-stop`）。

## 铁律

```
先把症状追溯到负责机制，再改代码
只改拥有错误行为的最窄层
不夹带 fix 之外的清理、重命名、抽象
regression proof 只覆盖本任务
```

## 工作流程

### 1. 复现失败（先于修复）

- 能经济地复现时**先复现**：写下可重复的最小步骤，得到失败证据。
- 无法复现时，收集**最强可得证据**（日志、堆栈、用户报告、快照、监控），而不是凭猜测动手。
- 用 `test-driven-development` 把复现固化为一个**失败的回归测试**：watch it fail → 修复 → watch it pass。

### 2. 溯源到负责机制

- 从 symptom 追到 responsible mechanism（见 `systematic-debugging` / `investigate-first`）。
- 区分**症状位置**与**根因位置**：坏值从哪里产生，谁在这里用了坏值。
- 不要在输出端给症状打补丁；修复点应在源头或拥有该 invariant 的层。

### 3. 在最窄责任层改动

- 选择**拥有该错误行为**的最窄 layer（函数 / 模块 / adapter / 边界）。
- 不要为了「更优雅」把修复搬到更宽或更窄的层，除非那才是真正的 owner。
- 若发现真正的修复需要重构 ownership，参照 `safe-refactor` 的边界纪律，并考虑拆成独立变更。

### 4. 保护无关行为与用户改动

- **保留无关行为**：不改动与 bug 无关的语义、错误模式、顺序、兼容性。
- **保留用户改动**：不要回退或覆盖用户 / 上游未提交的修改。
- 不理解的注释与代码不要删。

### 5. 只加任务相关的 regression proof

- 只添加能证明「该失败已修复」的最小测试。
- 不添加与任务无关的测试、不扩大覆盖率竞赛、不做顺手重构。
- 回归测试必须经过 red-green 验证（先失败、后通过）。

## 停止条件

- 跑 **focused proof**：聚焦的回归测试 / 复现步骤。
- 再跑 **nearest affected gate**：与改动最相关的既有测试套件 / 构建 / lint。
- 当**失败已修复且 regression proof 通过**时，立即停止。
- 按 `verification-before-completion` 给出命令与结果，不用「应该修好了」。

## Checklist

- [ ] 已复现失败，或已记录最强可得证据
- [ ] 已追溯到 responsible mechanism，修复点在根因而非症状
- [ ] 改动落在拥有该错误行为的最窄层
- [ ] 无关行为、错误模式、顺序、兼容性未被改动
- [ ] 未回退或覆盖用户 / 上游改动
- [ ] 未夹带 fix 之外的清理、重命名、抽象
- [ ] 新增的只有本任务的 regression proof，且经过 red-green
- [ ] focused proof 与 nearest affected gate 均通过

## 常见合理化

| 合理化 | 现实 |
|--------|------|
| 「顺手把这行也重构了」 | 混入无关改动，评审与回退都变难；拆成独立变更。 |
| 「症状这里加个判断最快」 | 症状补丁掩盖根因，坏值继续在别处扩散。 |
| 「复现太麻烦，先改了看」 | 没有失败证据，无法证明真的修好，也写不出回归测试。 |
| 「回归测试顺便多写几个」 | 只加任务相关的 proof，其余是 scope 蔓延。 |
| 「逻辑一样，顺手改个名」 | 重命名属于结构变更，不是修复；混在一起会让 diff 失真。 |

红旗：无失败证据就改代码；在输出端打补丁；借修复夹带重构/重命名；回退用户改动；回归测试没先失败过就宣称有效。

## 相关技能

- `investigate-first` / `systematic-debugging`：原因不明时先诊断，命名机制后再改。
- `test-driven-development`：把复现写成失败的回归测试。
- `verification-before-completion`：修复通过前给出新鲜证据。
- `safe-refactor`：当修复确实需要结构编辑时，用验证夹住它。
- `lean-build`：当请求其实是新行为而非 bug 时改走该路径。
- `code-review-and-quality`：修复与回归测试一并评审。
- `bug-lesson`：需要查历史踩坑并沉淀 bug 笔记时使用。
