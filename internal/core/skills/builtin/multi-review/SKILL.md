# multi-review：多专家两轮审查

工作流族 skill。**重大改动合入前**，用多个独立专家视角并行审查，两轮收敛，最大化发现单视角盲区。它是合并前的**会审门**，不是逐任务的日常评审门。

## 何时用 / 不用

**用**：

- 重构、安全敏感、核心逻辑等重大改动的合并前把关。
- `bug-lesson` 修复的重大 bug，落地前。
- rulebook（如 `docs-rulebook` 类规范）评审发现的债务整改，落地前。

**不用**：

- 单文件小改动、日常 PR —— 用 `code-review-and-quality`。
- 需要"实现 → 评审 → 修复"的逐任务闭环 —— 用 `subagent-driven-development`。

## 核心约定

1. **多专家视角用 Agent 工具并行派出**，**放在同一条消息**里（同条回复多个调用 = 并行；一条回复一个 = 串行）。每个专家独立产出审查意见，第一轮互不通气。
2. **两轮制**：第一轮各出意见 → 汇总去重 → 第二轮交叉复核**争议点** → 总控裁决。
3. **审查产出按严重度分级**（`blocker` / `major` / `minor` / `nit`），**每条附文件行号与修复建议**。

## 专家角色（第一轮，按改动性质取 3-5 个）

每个专家是一个独立子代理，只对一个视角负责，避免"什么都看一点"：

| 角色 | 关注点 |
|------|--------|
| Correctness / Logic | 边界、error path、off-by-one、race、状态一致性、是否真解决目标问题 |
| Security | 输入验证、secret 泄漏、authz/authn、注入、外部数据按不可信处理 |
| Architecture / Maintainability | 模块边界、依赖方向、是否引入新模式、可读性、重复与死代码 |
| Test Quality | 测试是否验证真实行为而非 mock、边界覆盖、断言强度、无断言测试 |
| Domain / Spec Compliance | 是否匹配 spec/需求（不多不少）、是否偏离既有约定、文档与代码是否一致 |

**角色裁剪规则**：让专家集合**恰好覆盖本次改动的主要风险面**；文件级局部改动可省略 Architecture，安全敏感必带 Security。

## 通信契约（每个专家的输出）

每位专家独立、**只报事实与证据**，不猜测其他专家的结论。统一输出格式：

```
## <角色> 审查意见
- severity: blocker | major | minor | nit
  location: <file>:<line>
  issue: <问题一句话>
  why: <为什么重要 / 触发条件>
  fix: <修复建议>
  evidence: <关键代码或命令输出片段>
```

- 每一条**必须**带 `file:line` 与 `fix`；无定位或无建议的意见视为无效。
- 严重度按实际影响定级，不夸大；blocker/major 必须有可复现或可论证的失败路径。
- 宁可少而准，不要堆砌。

## 两轮流程

### Round 1 — 独立出意见（并行）

1. 总控先固定审查范围：diff 范围（BASE..HEAD）、改动意图、绑定约束（spec 关键要求逐字复制）。
2. 同一条消息并行派出全部专家，每个拿到**相同范围 + 自己的视角**，互不告诉对方结论。
3. 收齐后总控**汇总去重**：合并同一处/同一根因的重复项，标出**专家间互相矛盾或存疑**的条目。

### Round 2 — 交叉复核争议点（并行）

只针对 Round 1 的**争议点与高严重度项**再派一轮（可用原专家，也可让每位专家复核**别人**的意见）：

- 任务：尝试**证伪或确认**这些结论，给出反例或补强证据，不得只复述。
- 交叉复核的目的是消除"某一位专家看走眼"带来的假阳性/假阴性。
- 复核仍不能定论的 → 升级给总控（或人类）裁决。

### 裁决与收敛

总控编辑最终清单：

- **blocker / major**：合并前必须修复；修复后**只对修复点重跑相关专家**，确认闭环。
- **minor**：本轮处理，或显式记录"延期 + 理由 + 负责人"。
- **nit**：可忽略。
- 专家意见与计划/spec 文本冲突时，**并列展示意见与原文，由人类裁决**，不擅自从一。

## 决策规则

- **不 rubber-stamp**：没有证据的"LGTM"无效。
- **不软化真问题**：会出生产事故的问题不得写成 "might be a minor concern"。
- **不预判**：派专家时不得说"不要标记 X""最多 minor"。
- **量化优先**："这个 N+1 让列表每项多 ~50ms" 优于 "可能有点慢"。
- 分歧裁决优先级：技术事实与数据 > style guide > 设计原则 > 代码库一致性。
- 高严重度发现与专家人数无关：**一个 blocker 也照样 block**。

## 收敛清单

- [ ] 审查范围、意图、绑定约束已固定并共享给所有专家。
- [ ] 第一轮并行派出，各专家独立、无串通。
- [ ] 已汇总去重，争议点已列出。
- [ ] 第二轮已对争议点/高严重度项做交叉复核，且给出新证据。
- [ ] 每条意见都有 severity + `file:line` + fix。
- [ ] blocker/major 已修复并复核闭环；minor 已处理或显式延期；nit 已归档。
- [ ] 与 spec/计划冲突项已交给人类裁决。
- [ ] 审查报告按 `docs-rulebook` 归档，路径可追溯。

## 相关技能

- `code-review-and-quality`：五轴评审、严重级标签与批准标准；本技能是其"多专家 + 两轮"的加重版。
- `dispatching-parallel-agents`：同一条消息并行派发的机制与提示结构。
- `subagent-driven-development`：逐任务的 spec + quality 评审门（本技能用于合并前会审）。
- `docs-rulebook`：审查报告等文档的目录与生命周期规范。
