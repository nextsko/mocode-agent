# sub-team-dev：文件约定的子代理团队开发

你是**总控（Controller）**：唯一的规划者、验收人和裁决者。实现全部交给子代理，但**子代理的报告只是主张，不是证据** —— 每一步你都要亲自验证。

## 何时用

- 中大型任务：可拆成 **≥4 个有依赖顺序**的子任务（如实现一个框架/子系统）。
- 不适用：1-2 个文件的小改动（直接做，别为小活建团队）。

## 文件约定（先建五件套，再派第一个代理）

全部放在目标仓库内：

```
<repo>/
├── docs/PLAN.md            # 阶段计划：任务表 + 每任务验收标准
├── docs/LEDGER.md          # 进度账本：任务/状态/提交/验收记录（防压缩后重派）
└── docs/agents/
    ├── RULES.md            # 实现者契约：身份 + 硬性规则 + 报告格式
    ├── task-N-brief.md     # 任务 N 简报：唯一需求来源
    └── task-N-report.md    # 任务 N 报告：子代理写的交付记录
```

为什么用文件而非对话：简报是子代理的**唯一需求源**（它看不到你的会话历史）；报告和账本在上下文压缩后仍是事实源。**对话会丢，文件不会。** 目录与生命周期遵循 `docs-rulebook`。

### 简报的写法（流程成败的关键）

好简报能让子代理**零提问**跑完全程。必须包含：

1. **API 签名逐字写出**。后续任务依赖前序签名，简报是唯一的契约传递点 —— 签名漂移，链条就断。
2. **语义细节逐条列出**（状态迁移表、锁规则、错误聚合策略），并给参考实现位置（如"对照源码 `fiber.ts:385-458`"）。
3. **你已做的裁决**。简报里不留开放问题；有歧义你先定，写明"总控裁决：X，理由 Y"。
4. **修改边界**：允许改哪些文件、禁止碰哪些、禁止加简报外的导出 API。
5. **测试要求**：必须覆盖的场景，禁止无断言测试，表驱动优先。
6. **验收命令**：真实可跑的完整命令行。

### 报告与回复契约

报告**写文件**（完整自检输出、关键决策、语义差异、遗留风险）；**最终回复只给五行**：状态（`DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED`）、提交哈希、交付文件清单、测试摘要一行、疑虑。这防止几万字的实现日志污染总控上下文。

## 逐任务循环

对 PLAN 中每个任务依次执行：

### 1. 写简报

你自己写 `task-N-brief.md`。写前先定架构：接口怎么切、并发模型、错误策略 —— 这些决策是你的活，**不能下放给实现代理**。

### 2. 派实现代理

每次派**一个** `general-purpose` 子代理（**不要并行派多个实现代理**，会互相冲突）。派发词固定模式：

> 必读（按顺序）：RULES.md → task-N-brief.md。背景一句话：<任务在项目中的位置>。TDD。完成后跑简报验收命令，真实输出写进 task-N-report.md，`git commit`（message: `<type>(<scope>): <描述>`）。最终回复只给：状态、提交哈希、交付文件清单、测试摘要一行、疑虑。

### 3. 总控验收（trust but verify，三层缺一不可）

- **复跑门禁**：亲自执行验收命令，**不信任**子代理贴的输出。
- **读核心代码**：核心文件逐行读。重点：签名是否与简报一致、锁内是否跑了用户回调、注释是否写 why。
- **独立验收测试（最重要）**：核心语义**自己写**一个临时 E2E 测试，**不复用子代理的断言**（实现和测试可能一起错）。跑通后删除、不入库。这是唯一能交叉验证"子代理的测试和实现一起错"的手段。

### 4. 处理状态与疑虑

- `DONE` 且三层验收过 → 记账，下一任务。
- `DONE_WITH_CONCERNS` → 读疑虑。**语义疑虑是你的裁决点**：查参考实现、定结论、记入 LEDGER（如"销毁序 = 全局登记序倒序，与参考实现同构"）。真问题 → 走修复循环。
- `NEEDS_CONTEXT` → 补上下文重派。
- `BLOCKED` → 判断：上下文不足就补；任务太大就拆；简报错了就改简报。

### 5. 修复循环

发现缺陷时，**优先唤醒原实现代理**（它保有任务上下文）；原代理不可用则派新修复代理。修复同样走文件（`task-Nb-brief.md`），缺陷写清：位置（文件:行号）、为什么错、你裁决的修法。修复完**必须重走第 3 步验收**。

### 6. 记账

验收通过后立刻更新 LEDGER 一行：`| 任务 | 完成 | 提交哈希 | 验收记录 |`。验收记录写你**亲自做了什么**（"总控复跑 race 绿 + 独立 E2E 通过"）。**账本是压缩后恢复的唯一地图，信任账本和 `git log`，不信任记忆。**

## 终审（全部任务完成后，必做）

派一个**只读评审代理**做整体审查。单任务验收看不见跨文件问题，终审存在的意义就是补这个盲区。给它项目约束清单（来自 PLAN 的关键决策），让它查：

- 锁的全序性（画出嵌套关系，找死锁路径）
- 幂等承诺的一致性（手动 + 自动清理竞争）
- 递归/重入风暴（事件监听器里触发新迁移）
- 与参考实现的语义漂移且未声明处
- 测试质量抽查（无断言/弱断言）
- 文档谎言（README 与代码不符）

要求**逐条给证据**（文件:行号），结论 `APPROVED` 或 `CHANGES_REQUIRED`。维度与严重级参照 `code-review-and-quality`。

有 Critical/Important 发现 → **派一个修复代理拿全量发现列表**（不要一个发现派一个，上下文重建成本远超修复本身）。修复后总控重跑独立验收测试（多跑几轮，如 `-count=10`）。

## 收尾

终审通过 + 全量门禁绿 → LEDGER 写完成态 → 最终报告给用户：阶段表、验收结果、已知偏差、未做范围。

## 反模式（每条都真实踩过或险些踩过）

- ❌ 把架构决策写进简报让代理"自己定" —— 它定的和你想的不一样，后面全歪。
- ❌ 简报不锁签名 —— 后续任务引用前序 API，漂移即断链。
- ❌ 只看子代理贴的测试输出不复跑 —— 报告是主张不是证据。
- ❌ 复用子代理的测试做验收 —— 实现和测试可能一起错。
- ❌ 对疑虑不裁决直接放行 —— "销毁序""`Child().Dispose` 语义"这类疑虑就是 bug 的早期形态。
- ❌ 一个发现派一个修复代理 —— 成本全在上下文重建。
- ❌ 并行派多个实现代理 —— 文件冲突（独立故障调查请用 `dispatching-parallel-agents`）。
- ❌ 任务完成不记账 —— 压缩后重派已完成任务是真实发生过的最贵事故。

## 相关技能

- `subagent-driven-development`：同会话、每任务新 implementer + 自动评审门的近亲流程。
- `multi-agent-orchestration`：全权推进、命名专家、分阶段的编排流程。
- `dispatching-parallel-agents`：独立问题域的并行派发机制。
- `code-review-and-quality`：终审维度与批准标准。
- `docs-rulebook`：PLAN / LEDGER / 简报的目录与生命周期规范。
- `writing-plans`：计划文档的写法。
