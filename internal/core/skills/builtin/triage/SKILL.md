# Triage（问题分诊）

## 概述

把 issue（以及被视为请求面的外部 PR）沿一组 **triage 角色**推进的小型状态机。

- **PR 即「附带代码的 issue」**：使用同一套角色、状态与状态机，仅少数地方标注「for a PR」。
- 裸 `#42` 按 tracker 配置解析为 issue 或 PR。
- 每个被 triage 的条目应恰好带**一个 category 角色 + 一个 state 角色**。

## AI 声明（强制）

triage 期间向 issue tracker 发布的**每条评论或 issue 都必须**以以下声明开头：

```
> *This was generated by AI during triage.*
```

## 角色

### Category（分类，二选一）

- `bug`：某处坏了
- `enhancement`：新功能或改进

### State（状态，五选一）

- `needs-triage`：维护者需评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：已完整指定，可交给 AFK agent
- `ready-for-human`：需要人类实现
- `wontfix`：不会被处理

**for a PR**：同一批状态针对附带代码来读——`ready-for-agent` 表示已附 brief、agent 应接手 diff 的下一步；`ready-for-human` 表示可由人类合并。

角色名是**规范名**，tracker 里的实际 label 字符串可能不同，映射应由配置提供；缺失时提示用户运行 `/setup-matt-pocock-skills`。

## 状态机

```
（未标记） ──→ needs-triage ──┬──→ needs-info ──（报告者回复）──→ needs-triage
                             ├──→ ready-for-agent
                             ├──→ ready-for-human
                             └──→ wontfix
```

- 状态角色冲突时，**先标记并询问维护者**，再做其他事。
- 维护者可随时覆盖；对不寻常的转换要标记并询问。

## 调用

维护者以自然语言调用 `/triage`，解释请求并执行。示例：

- 「Show me anything that needs my attention」
- 「Let's look at #42」（issue 或 PR）
- 「Move #42 to ready-for-agent」
- 「What's ready for agents to pick up?」

## 展示待处理事项

查询 tracker，按 oldest first 呈现三个 bucket：

1. **Unlabeled**：从未 triage
2. **`needs-triage`**：评估进行中
3. **`needs-info` 且上次 triage 之后报告者有活动**：需重新评估

PR 在范围内时，把外部 PR 纳入这些 bucket，并逐行标注 `[PR]` / `[issue]`。发现阶段只暴露**外部** PR（由 tracker 配置定义谁是外部）；协作者的进行中 PR 不算 triage 工作——该过滤仅用于发现，被显式点名的 PR 无论作者一律 triage。

展示计数与每项一行摘要，让维护者挑选。

## Triage 一个具体 issue / PR

1. **收集上下文**：读全文（body、评论、labels、作者、日期；PR 还要读 diff），解析既有 triage 笔记以免重复提问；用领域词汇探索代码库，尊重相关 ADR。对代码库做两项检查：
   - **冗余检查**：按**领域概念**（而非请求措辞）搜索是否已有该行为的实现，并报告搜索过的位置。若已实现 → 属于「already-implemented wontfix」（见第 5 步）。
   - **既往拒绝检查**：读 `.out-of-scope/*.md`，浮出任何相似条目。
2. **推荐**：给出你的 category 与 state 建议及理由，附与该请求相关的简要代码库摘要（含是否已实现）。等待指示。
3. **验证主张**：在任何 grilling 之前先验证。bug 按报告者步骤复现；PR 确认 diff 名实相符（checkout、跑相关测试 / 命令）。报告结果：confirmed（附代码路径）、failed、或细节不足（强烈的 `needs-info` 信号）。已验证的复现能让 agent brief 强得多。
4. **Grilling（必要时）**：若请求需要补充成型，调用 Skill（"grilling" 与 "domain-modeling"），一次一轮问题打磨领域术语，并随决策落地同步更新 `CONTEXT.md` / ADR。
5. **落地结果**：
   - `ready-for-agent`：发布 agent brief 评论（见下）。
   - `ready-for-human`：结构与 agent brief 相同，但注明为何不能委派（判断、外部访问、设计决策、手动测试）。
   - `needs-info`：发布 triage notes（模板见下）。
   - `wontfix`：关闭，评论取决于**原因**：
     - **already implemented**：改动已存在于代码库——指出它在哪里；**不要**写 `.out-of-scope/`（该 KB 用于被拒绝的请求，不是已构建的）。
     - **rejected (bug)**：礼貌解释后关闭。
     - **rejected (enhancement)**：写入 `.out-of-scope/`，评论中链接，再关闭。
   - `needs-triage`：应用角色；如有部分进展可附可选评论。

## 快速状态覆盖

维护者说「move #42 to ready-for-agent」时，信任并直接应用角色；执行前确认要做的动作（角色变更、评论、关闭），跳过 grilling。若在未 grilling 的情况下移到 `ready-for-agent`，询问是否需要写 agent brief。

## Agent Brief（写入 `ready-for-agent` 的结构化评论）

它是 AFK agent 工作的**权威规格**；原 body 与讨论只是上下文。原则：

- **Durability over precision**：条目可能滞留数天 / 数周，代码会变。描述 interfaces / types / behavioral contracts，点名类型、函数签名、config 形状；**不要引用文件路径或行号**。
- **Behavioral, not procedural**：说 **what**，不说 **how**。
- **Complete acceptance criteria**：每条独立可验证。
- **Explicit scope boundaries**：写明 out of scope。

模板：

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** one-line description of what needs to happen

**Current behavior:**
Describe what happens now.

**Desired behavior:**
Describe what should happen, including edge cases and error conditions.

**Key interfaces:**
- `TypeName`: what needs to change and why
- `functionName()` return type: current vs desired
- Config shape: any new options

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2

**Out of scope:**
- Thing that should NOT be changed
- Adjacent feature that is separate
```

## `.out-of-scope/` 知识库

存放**被拒绝的 enhancement 请求**的持久记录，用于机构记忆与去重。

- 结构：每**概念**一个文件（不是每 issue 一个），kebab-case 命名，如 `dark-mode.md`、`plugin-system.md`。
- 文件内容：`# Concept Name` 标题、`**Decision:**`、`**Reason:**`、`**Prior requests:**` 列表（含 issue 链接）。
- 理由要**持久**：引用项目范围 / 哲学、技术约束或战略取舍；不要写「最近太忙」这类临时情形（那是延期，不是拒绝）。
- 匹配按**概念相似度**，不是关键词：「night theme」应命中 `dark-mode.md`。
- **只在 enhancement 被拒时写入**；already-implemented 的 wontfix **不写**，否则会污染去重检查。
- 维护者改变主意时：删除对应 `.out-of-scope/` 文件，旧 issue 作为历史不重开，新 issue 走正常 triage。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把 grilling 中已解决的问题都归入「established so far」以免丢失；问题必须具体、可执行，不能写「请提供更多信息」。

## 恢复上一次会话

若已有 triage 笔记：先读，检查报告者是否回答了未决问题，先呈现更新后的图景再继续；**不要重复询问已解决的问题**。

## Checklist

- [ ] 每条对外评论 / issue 以 AI 生成声明开头
- [ ] 条目恰好一个 category + 一个 state 角色
- [ ] 已做冗余检查与 `.out-of-scope/` 既往拒绝检查
- [ ] 已先验证主张（复现 / 确认 diff）再 grilling
- [ ] agent brief 不含文件路径 / 行号，含可测试 acceptance 与 scope 边界
- [ ] already-implemented 的 wontfix 未写入 `.out-of-scope/`
- [ ] needs-info 问题具体可执行，已保留 established so far

## 相关技能

- `grilling` / `domain-modeling`：把请求打磨成型、统一领域术语。
- `verification-before-completion`：验证主张、写「confirmed」时以证据为准。
- `code-review-and-quality`：评估 PR 附带代码的质量。
- `bug-lesson` / `systematic-debugging`：复现 bug 与根因定位。
- `docs-rulebook`：`.out-of-scope/` 等知识产物的组织纪律。
