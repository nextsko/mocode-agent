# bug-lesson：修 bug 前后必做

## 概述

修 bug 不是「改到不报错」就结束。这是一个**闭环工作流**：修前检索历史踩坑 → 用结构化方法溯源 → 带回归测试修复 → 修完沉淀笔记，让下一个同类问题不必从零诊断。

核心一句话：**先查历史，再溯源，修复必带回归测试，修完必留笔记。**

## 何时使用

- 修任何 bug、排查报错 / 崩溃 / 异常行为
- 触发词：「这个报错怎么回事」「帮我修一下」「为什么挂了」「排查一下」「定位一下」
- 问题看起来似曾相识，可能以前踩过同类坑

## 铁律

```
修之前先检索知识库，命中配方就按诊断路径走
不修表象，只修根因
每个 bug 修复必须附带能复现原故障的回归测试
修完必须沉淀 bug 笔记
```

## 工作流程

### 1. 修之前：检索历史踩坑

- 检索知识库的 **bugs** 与 **bug-recipes** 两类记录（默认根目录 `/data/fromsko/kng/knowledge/`，入口见其 `INDEX.md`）。
- 按**技术关键词** grep，而不是只按报错原句；命中则先按配方里的**诊断路径**走，避免重复诊断。
- 找不到命中也要记录「查过哪些关键词、排除过哪些疑似记录」。

### 2. 溯源：按逻辑树 / 逻辑链定位根因

- 用**逻辑树 / 逻辑链**拆解问题，从 symptom 逐层追到 root cause（方法论参见 `exps/rules/08-problem-solving.md`）。
- 记录**为什么先排除某些假设**——诊断路径本身就是宝贵信息。
- 不修表象：在症状处打补丁会掩盖根因。
- 与 `systematic-debugging`、`investigate-first` 配合：证据不足不下手。

### 3. 修复：必须带回归测试

- 按 `exps/rules/07-bug-fix-workflow.md` 的修复纪律执行。
- **每个 bug 修复必须附带一个能复现原故障的回归测试**：先 watch it fail，再修复，再 watch it pass（见 `test-driven-development`）。
- 修复落在拥有该错误行为的最窄责任层（见 `surgical-patch`）。
- 无回归测试的修复视为未完成，不得声明已修好（见 `verification-before-completion`）。

### 4. 修完：沉淀笔记

- **简单踩坑**：写入知识库 `bugs/`（索引级记录）。
- **完整诊断过程**：按 `bug-recipe-template.md` 写入 `bug-recipes/`，必须包含 **Regression Guard**。
- 写入后**重跑索引脚本**，让记录可被检索。
- 重大 bug 修复完成后，可联动 `multi-review` 做多专家把关。

## 约定

- 文件名格式：`编号-主题-技术-动作.md`，编号续编，不重号。
- bug 笔记必须写清五项：
  - **症状**：外部可观察的异常表现
  - **根因**：真正负责的机制
  - **诊断路径**：为什么先排除了哪些假设
  - **修复**：改了哪个最窄层，为什么
  - **回归测试位置**：文件与用例名
- 测试位置与诊断路径要可被他人复用，而非只写「已修复」。

## Checklist

- [ ] 修前已按技术关键词检索 bugs / bug-recipes，并记录命中或排除
- [ ] 已用逻辑树 / 逻辑链追到根因，而非在症状处打补丁
- [ ] 诊断路径（排除了哪些假设、为什么）已记录
- [ ] 回归测试先失败、后通过
- [ ] 修复落在最窄责任层，未波及无关行为
- [ ] 已沉淀笔记（简单→bugs/；完整→bug-recipes/，含 Regression Guard）
- [ ] 已重跑索引脚本
- [ ] 有命令输出支撑「已修复」的结论

## 常见合理化

| 合理化 | 现实 |
|--------|------|
| 「这问题很简单，不用查历史」 | 简单问题常是重复踩坑；检索成本远低于重复诊断。 |
| 「先改到不报错再说」 | 症状补丁掩盖根因，bug 会换一种形式回来。 |
| 「修复太急，测试后补」 | 无回归测试就无法证明原故障被修复，也无法防复发。 |
| 「修完就算了，笔记以后写」 | 以后的笔记不会写；知识不沉淀，下次还得从零排查。 |

红旗：不查知识库直接开修；在症状处打补丁；修复无回归测试；笔记缺根因/诊断路径；改完不重跑索引。

## 相关技能

- `systematic-debugging` / `investigate-first`：根因调查的端到端纪律。
- `surgical-patch`：修复落在最窄责任层。
- `test-driven-development`：把原故障固化为失败回归测试。
- `verification-before-completion`：声明「已修复」前给出新鲜证据。
- `code-review-and-quality`：修复与回归测试一并评审。
