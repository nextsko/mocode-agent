# handoff：会话交接文档

把当前会话总结成一份**交接文档**，让一个全新代理能接手续做。核心原则：**读者没有你的上下文，只能靠这份文档 + 磁盘上的产物**。

## 何时用

- 上下文即将耗尽，工作需在下一会话继续。
- 任务跨会话、跨代理移交。
- 用户要求"交接/总结当前进展给下一个 agent"。

## 保存位置

保存到**操作系统临时目录**，**不要**写进当前工作区：

- Windows：`%TEMP%`（如 `C:\Users\<user>\AppData\Local\Temp\`）
- macOS / Linux：`$TMPDIR` 或 `/tmp`

文件名带主题与日期，便于识别：`handoff-<topic>-<YYYY-MM-DD>.md`。

## 必须包含的内容

1. **目标与范围**：这次会话要达成什么、验收标准是什么。
2. **当前状态**：已完成 / 进行中 / 未开始，逐项一句话，附提交哈希或产物路径。
3. **下一步**：接手者应从哪一步开始，第一个可执行动作是什么。
4. **关键文件与路径**：代码、计划、spec、日志、diff 的**绝对路径**。
5. **决策与约束**：已拍板的架构/接口决策**及理由**，以及不能偏离的约束 —— 避免接手者重新争论已定之事。
6. **坑与注意事项**：已知失败模式、易踩的步骤、需要提前知道的 workaround。
7. **suggested skills**：明确列出下一个代理应调用哪些 skill（按名字），并一句话说明各自用途。

## 写作纪律

- **不要重复既有产物**：spec、plan、ADR、issue、commit、diff 里已有的内容，**按路径或 URL 引用**即可，不要抄进交接文档。交接文档是"索引 + 状态 + 意图"，不是内容搬运。
- **脱敏**：API key、密码、token、个人可识别信息（PII）一律**删除或打码**，不得写入。
- **区分事实与主张**：状态用可核查的证据（文件路径、命令输出、提交哈希）支撑，不要只写"应该没问题"。
- **面向行动**：每条陈述都服务于"接手者接下来做什么"，删掉无助于此的叙事。

## 模板

```markdown
# Handoff: <主题>
> 生成时间：<ISO 时间>；源会话：<会话/任务标识>

## 1. 目标与验收标准
<一句话目标 + 可核查的完成条件>

## 2. 当前状态
- ✅ 已完成：<项> —— <证据：提交哈希/文件路径>
- 🚧 进行中：<项> —— <卡在哪、已到哪一步>
- ⬜ 未开始：<项>

## 3. 下一步（从这里开始）
1. <第一个可执行动作，含确切命令/文件>

## 4. 关键文件与路径
- 计划：<绝对路径>
- 代码：<绝对路径>
- 产物/日志：<绝对路径>

## 5. 决策与约束（不得重新争论）
- <决策> —— 理由：<...>
- 约束：<...>

## 6. 坑与注意事项
- <已知失败模式 / workaround>

## 7. 按引用而非复制
- spec：<路径/URL>
- plan：<路径/URL>
- ADR / issue / commit / diff：<路径/URL>

## 8. Suggested skills
- `<skill-name>` —— <用途>
- `<skill-name>` —— <用途>
```

## 参数处理

若用户传入了参数，把它当作"**下一次会话将聚焦什么**"的描述，据此裁剪文档：突出与该焦点相关的状态、文件、决策与坑，淡出无关内容。

## 相关技能

- `docs-rulebook`：交接中引用的计划/文档应遵循的目录与生命周期规范。
- `writing-plans`：若下一步需要产出/续写计划。
- `verification-before-completion`：交接前用新鲜证据核对"已完成"的状态。
- `subagent-driven-development` / `sub-team-dev`：交接后接手者若继续多任务执行可参考的流程。
