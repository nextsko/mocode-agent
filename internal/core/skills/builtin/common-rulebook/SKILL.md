# common-rulebook：组织级规范方法论与普适原则

> **两层结构中的方法层**：本 skill = 萃取方法论（§1–2）+ 跨栈普适原则（§3–4）。各组织的具体参数住在实例层 skill（如 `ooml-rulebook`）。
> **使用顺序**：① 查实例层 rulebook——有则同时加载，冲突时实例参数优先；② 无则按 §1 现场萃取；③ 评审先用 §3 普适原则，再用实例参数。

## 1. 方法论：组织规则萃取十步法

每一步都可由并行子代理承担。

1. **全量侦察（先画版图再下钻）**——跨仓依赖矩阵（`rg "org-name/"` 统计引用，产出"谁依赖谁"）；逐仓 `git log -1 --format=%cs` 分活跃核心 / 近期维护 / 停滞 / 疑似弃用四档；识别"被引用但不在场"的外部仓库（隐形架构边界）。产出分层版图 + 枢纽仓库清单。
2. **域聚类分组委派**——按逻辑域（基础设施/平台/产品/能力资产/外围）而非目录大小聚类；每组一个并行调研者，统一模板产出：①一句话定位 ②技术栈 ③架构与关键抽象 ④设计决策 ⑤跨仓关联 ⑥风险观察；旗舰仓细读、小仓快过、死仓只做验尸。
3. **证据纪律（反幻觉铁律）**——每条规则标注 `仓库名/路径` 级出处；读不到源码的结论标注为推断；配置类规范引用配置原文而非凭印象转述；只把"多仓一致（普遍规律）"写成规范，单仓例外另行标注。
4. **反模式从事故蒸馏（最值钱的一步）**——从真实事故反推禁令：同名包双仓、副本分叉、死 fork 无声明、凭证落仓、CORS 裸开……格式 `❌ 禁止 X | 依据：某仓某事故`。原则：一条经历过的教训胜过十条倡议——倡议被忽略，禁令被记住。
5. **世代分层（承认历史，不一刀切）**——工具链/风格按"仓库世代"分层描述并标注每代现役范围；新仓默认最新代，老仓"风格随仓库现状，不跨仓统一"。永远不给有历史的组织"单一答案"。
6. **哲学先于规则（宪法结构）**——顶部提炼 3–6 条设计哲学（一句话一条），细则从哲学派生；评审顺序先哲学（架构级否决权）后细则；写不出 why 的降级为细则。
7. **豁免机制（防教条化）**——每条硬规则声明边界条件：宿主/平台钦定的依赖不扣分、第三方生态命名遵循宿主惯例、一次性营销/实验仓降标准。豁免写进规则本体（"X 除外，因为 Y"），不是评审时临时解释。
8. **checklist 落地**——规范收口为"新项目启动 checklist"（约 12 项，每项指回章节号）；checklist 是唯一执行入口——没人翻 300 行规范，但人人会勾 checklist。
9. **防泄题实测**——选调研中挖掘最浅的仓库实测评审；产出必须结构化（合规/违规/豁免）+ 证据到行号 + 与调研结论无重叠；全是背答案或全是误报则回炉第 3/6 步。
10. **定期重蒸馏（防腐化）**——每 6–12 个月重跑第 1–2 步，diff 出新世代/新事故/新弃用；腐化信号：规则引用的仓库已弃用、两派风格各占半壁、查不到出处的"口口相传"规则。版本化 rulebook（标注快照日期），过时规则降级为"历史观察"而非直接删除。

## 2. 规则书写规范

**三要素（缺一不写）**：① **具体值**——"并发上限 6"而非"要限流"，"min(30s, 2^attempt×1s)"而非"指数退避"；② **出处**——`仓库名/路径`；③ **反例**——违反会发生什么（引用真实事故更佳）。

**三类本质（先分类，冲突时按类裁决）**：

| 类别 | 判定 | 处理 |
|---|---|---|
| 最佳实践 | 有业界收敛（OWASP/Git 本身等佐证），解决结构性问题 | 可跨组织平移，违反=缺陷 |
| 口味/家法 | 多个合理选项中选了一个，一致性本身是价值 | 组织内强制，组织间无意义，禁止包装成"最佳实践" |
| 业务决策 | 许可证策略、白标设计、分发渠道等商业选择 | 只在组织语境下有效，换环境必须重议 |

## 3. 普适原则层（跨栈/跨组织成立，违反=缺陷）

### 3.1 信任边界
- **凭证边界**：密钥/OAuth 生命周期收拢在最小信任域（网关/主进程/凭证服务），消费方只见结构化结果与安全账户标签，永不见原始 token；配置存引用（env 名/别名）不存值。
- **fail-closed**：能力缺失时拒绝而非降级放行；用户代码在隔离域只拿窄能力，任务结束即收权。
- **权限只收窄不扩展**：多层策略叠加时每层只能减权限。
- **出站守卫**：所有外部请求经统一守卫（URL/重定向/DNS 解析后地址逐跳校验）；私网访问需显式声明贯通。
- **静态加密为默认**；token 库存哈希、仅显示一次；常量时间比较；防并发单飞。

### 3.2 状态与演化
- **不可变事实 + 可变指针**：历史不改写，回滚=新建记录；发布版本化，改名靠兼容别名保活。
- **断点续跑是默认**：长管线中间产物落盘为稳定契约（路径/格式文档化），每阶段可独立重放；请求级内容哈希缓存只存成功响应、原子写入。
- **兼容层平滑换代**：新代保留旧参数仅兼容解析并文档化优先级；破坏性变更加 `!` 与迁移文档。
- **借协议不建轮子**：先问"有没有成熟协议可寄生"（registry 协议/OIDC/MCP/SSH），自建是最后选项。
- **发行版而非 fork**：pin 上游 SHA + fail-closed 最小补丁 + 可变/只读层分离；fork 必须声明改动清单与上游跟随流程。
- **懒加载隔离上游故障**：重依赖延迟导入、pin 接入点、不暴露上游 factory——上游问题在上游仓库修。

### 3.3 认知与协作
- **渐进式发现**：大量能力压缩为少量发现工具（list→search→inspect→call），防注册爆炸/上下文爆炸——对 UI、CLI、Agent 工具、文档同样成立。
- **边界即合同**：架构文档定义 owner 模型（谁拥有什么），静态检查强制归属，越界在 CI 挂掉。
- **诚实性文档**：明确区分"已声明/可执行/已验证"三态与"不支持"的能力；未配置是正常状态而非错误。
- **架构测试硬门**：把纪律（隐私决策/契约对齐/依赖边界/泄漏扫描）写成会挂 CI 的测试，而非口头约定。
- **AI 文档层级**：`AGENTS.md` 载硬规则（不进 lint 的规则写这里）→ 薄入口索引 → 面向 Agent 的偏好声明（Preferred Usage）→ 契约文档只写用户可见契约。

### 3.4 LLM 时代扩展
- 请求级缓存（内容哈希 key、只存成功）+ 并发限流 + 成本计量（token 分列）内建；
- 结构化生成解耦：生成模型（高温）与结构回填（低温）两段式，修复回路设上限；
- 重试时采样参数递增以跳出坏样本，而非同参重试；
- LLM 是增强不是依赖：核心链路断网/无 key 可跑（启发式兜底）；
- 数据完整性优先于展示：只清洗确认的伪影，绝不静默改写用户内容；
- prompt 变更走 evals 回归。

## 4. 通用性判定：什么可平移，什么必须重写

- **可平移**：§3 全部（解决信任、状态、演化、认知等结构性问题）。
- **必须重测/重写**：工具选型与签名风格（口味）、命名 scope（组织身份）、色值与 UI 参数（品牌）、许可证矩阵与分发渠道（业务）。
- **失效条件**（调低适用范围）：① 单仓库小团队——生态级规则无用武之地，只留语言级与原则级；② 强监管领域——原则层是"产品级安全"不是"合规级安全"，缺审计追溯/数据留痕/可解释性；③ 领域错位——UI/LLM 章节随领域失效，§3.1–3.3 仍成立；④ 组织规模 < 5 仓库——第 1–2 步收益低，直接从第 3–6 步开始。

## 5. 产出模板：org rulebook 骨架

按此骨架填充（实例层 skill 遵循同一骨架，便于跨组织对照）：

```
0. 设计哲学（3–6 条，能解释 why）
1. 代码风格（按语言 × 按世代；两派并存时列表对照）
2. 工程脚手架（包管理/构建/monorepo/CI 三件套）
3. 测试规范（框架/组织/架构测试/coverage 门槛）
4. 错误处理（错误类范式/错误码风格/重试退避参数）
5. 命名与代码组织（scope/目录分层/严格度/禁 barrel）
6. 注释与文档（注释语言/多语言 README/AI 文档层级）
7. 版本与发布（占位版本/OIDC/changelog）
8. Git 惯例（commit 格式/分支/卫生文件）
9. 架构观念（N 律）
10. 安全清单
11. API/协议设计
12. 领域专项（LLM/UI/数据……按组织取舍）
13. 产品形态与分发
14. 仓库治理与许可证
15. 反模式禁令清单（❌ + 事故出处）
16. 新项目启动 checklist（指回章节号）
```

**配套要求**：标注快照日期与证据仓库名；豁免条件写进规则本体；rulebook 本身版本化。

## 6. 与实例层的协作协议

- 加载顺序：评审/写码 → 先加载实例层（如 `ooml-rulebook`），本 skill 作为方法与原则兜底。
- 冲突裁决：实例参数（工具/值/命名）> 本 skill 普适原则；实例若违反 §3，标记为"实例层债务"并报告，而不是静默服从。
- 新组织接入：用 §1 十步法产出新实例层 → 挂到 §5 骨架 → 第 9 步实测 → 纳入第 10 步重蒸馏周期。

## 相关技能

- `ooml-rulebook`：本方法论的 OOMOL 实例层，演示 §5 骨架的完整填充。
- `docs-rulebook`：文档与计划的目录/生命周期纪律，是规范产物的落地载体。
- `code-review-and-quality`：把规范要求接入评审五轴与批准标准。
- `writing-plans`：把规范要求转成可执行的实现计划。
- `systematic-debugging`：事故蒸馏与根因调查的方法支撑。
