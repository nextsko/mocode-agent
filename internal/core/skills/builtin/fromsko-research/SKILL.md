# fromsko-research：调研与项目研究

## 概述

研究与项目研究技能族。三种意图各走一条路由，统一产出可归档的调研结论。核心原则：**调研并行、结论归档、子 Agent 只回路径不回正文**。

本技能负责「拿到可信结论」；结论的落盘位置与生命周期参照 `docs-rulebook`。对单一项目做深入理解时改用 `project-teardown` 或 `reverse-engineering-docs`。

## 何时使用

- 多主题调研（通常 3–8 个独立主题，需并行查证）。
- 研究某个 git 仓库 / 开源项目 / 别人代码的实现方式。
- 生成组件树 / 依赖树 / 架构树 / 设计树，做代码溯源。

## 路由表

| 用户意图 | 执行方式 |
|---|---|
| 并行多主题调研（3–8 主题） | 派多个子 Agent 并行调研 + 知识沉淀 |
| Git 项目完整研究（四维度并行 + 书籍式产出） | 四维度并行深挖后汇总成体系化文档 |
| 代码溯源分析（组件树 / 依赖树 / 架构树 / 设计树） | 静态分析产出 mermaid 树图 |

选择规则：

- 主题之间**相互独立**且数量 ≥3 → 并行多主题调研。
- 目标是「读懂某个仓库」→ Git 项目完整研究。
- 目标是「这东西从哪来 / 谁依赖谁 / 结构如何」→ 代码溯源树图。

## 模式一：并行多主题调研

1. 把需求拆成 3–8 个**彼此独立**、边界清晰的调研主题。
2. 每个主题派一个子 Agent，**同一条消息内全部发出**（并行）。
3. 每个子 Agent 的输出契约必须自包含：调研问题、需要什么证据（源码/文档/版本）、输出格式。
4. 汇总时对每个主题给出 **Adopt / Reject 决策**及理由，而不是只罗列资料。
5. 结论归档，并在索引中登记。

## 模式二：Git 项目完整研究

四维度并行（可映射到 4 个子 Agent）：

| 维度 | 要回答的问题 |
|------|--------------|
| 定位与价值 | 项目解决什么问题、给谁用、与同类差异 |
| 架构与实现 | 分层、关键模块、核心类型/函数、数据流 |
| 工程与流程 | 构建、测试、CI/CD、发布节奏、贡献规范 |
| 历史与生态 | 版本里程碑、issue 主题、依赖与供应链 |

产出组织成**书籍式文档**（有目录、章节、交叉引用），而非零散笔记。

## 模式三：代码溯源树图

- **组件树**：UI/模块的父子与组合关系。
- **依赖树**：包/模块之间的导入依赖方向。
- **架构树**：分层与边界（入口 → 业务 → 数据）。
- **设计树**：设计意图/约束如何逐层落成代码。

产出用 **mermaid** 表达；每张图附数据来源与范围说明。

## 执行约定

- 子 Agent 用宿主平台自带的 `Agent` / `task` 工具（原文旧称 `mcp_task` / `generalPurpose`）派出，类型用 `general-purpose` 或 `Explore`；**多条并行放同一条消息**。
- 子 Agent 汇报**只回一行 `STORED: <路径>`**，不回正文，避免上下文膨胀；正文写入文件。
- 调研产出使用统一模板，逐条含 **Adopt / Reject 决策**与依据。
- 大规模、多仓库的体系化研究，可按 `common-rulebook` §1 的「萃取十步法」组织。
- 调研结论经知识归档流程入库，后续复用而非重查。

## 反模式

- 串行调研相互独立的主题（浪费并行预算）。
- 子 Agent 把整篇报告塞回主上下文（污染上下文）。
- 只收集资料、不给 Adopt/Reject 决策（调研没有结论）。
- 树图无来源、无范围说明（不可信）。
